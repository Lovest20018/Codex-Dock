## 优先处理的项目问题

### 1. 修正版本与默认值信息

| 字段 | 当前目录 | 核查结果 | 建议 |
| --- | --- | --- | --- |
| `features.reasoning_effort_override` | 开发中、默认 false | 稳定、默认 true | 修正元数据；其中文说明已经写了“稳定、默认开启”，两处目前矛盾 |
| `features.secret_auth_storage` | 稳定、默认 false | 稳定、默认 true | 根据实际内核版本显示默认值 |
| `features.code_mode_tool_description_first` | 开发中 | 已移除 | 放入只读历史资料，禁止新增配置 |
| `audio.microphone_channel` | 未限制下界 | 本次官方 schema 要求 minimum=1 | 补充校验，不接受 0 或负数 |

目前 `CatalogEntry.CanEdit` 和过滤逻辑直接使用快照的生命周期。因此元数据过期不仅影响说明，也可能把已移除字段当成可编辑项。

建议为目录补充官方来源、抓取日期、schema 哈希、已核查内核版本，以及兼容/别名/移除信息。默认值分成“本内核默认”“文件显式值”“继承值或未知”，不只展示一个 true/false。检测到不同版本时继续允许查看与保留配置，避免自动覆盖。

20 条新增路径应按本版本和产品范围补收，不全部开放给普通用户。其中包括 `auto_review.timeout_ms`、`features.rollout_budget.enforce_limit`、`memories.consolidation_service_tier`、供应商认证文件/区域/项目字段和部分新特性。`features.artifact` 只见当前内核特性列表，未见本次公开 schema，先作为诊断信息。

证据：`config/config-schema.json`、`ConfigSchema.cs`、当前二进制 `features list`、本次官方 JSON schema。

### 2. 增加“已配置”，展开真实命名实例

当前只有“常用 / 全部 / 已修改”。`SettingsEditor.Refresh` 展示静态定义；已被动态模板匹配的真实路径不会进入 `UnlistedEntries`。因此已有 MCP、provider、插件、项目等仍常表现为 `<name>` 模板，必须手工填路径才能查看具体实例。

建议把入口改成“常用 / 已配置 / 全部 / 已修改”，其中“已配置”直接展开真实实例，例如每个 MCP 服务、每个 provider、每个插件，显示本文件值和来源。添加新实例使用单独入口，不让用户先编辑 `<name>`。

已有两台 MCP 服务也应该显示两组配置，而不是一组静态模板。对本项目当前环境，本次只读检查确实发现两个 MCP 服务定义；服务名称、地址和凭据未导出。

MCP、provider、权限 profile 优先做结构化表单；任意 TOML 路径入口保留给高级使用。当前每页 30 项与搜索防抖可以保留，没有证据需要为 983 条目录整体重做渲染机制。

证据：`SettingsEditor.Refresh`、`ConfigSchema.UnlistedEntries`、`ConfigSchema.Find`。

### 3. 显示配置来源和实际作用范围

当前界面明确声明只显示本地文件，但用户仍容易把“保存成功”“跟随默认”理解成“当前聊天已采用”。建议增加只读的生效配置视图，按当前项目和所选执行端读取支持的 `config/read` 层信息，并与本文件并排显示。协议在本机导出的 `ConfigReadParams` 中已经有 `cwd` 和 `includeLayers`；这是可用接口依据，不代表本次完成了实际接入。

每项至少显示文件值、来源、客户端/执行端、需新聊天还是重启。会话参数和组织强制策略单独标注；解析不到时显示未知。桌面 `desktop.*`、CLI `tui.*`、Dock 自有设置、手机设置不要混成一套可互相替代的开关。

“恢复默认”可改为“取消本文件覆盖”，说明它删除的是本文件的值。新 profile 应使用 `$CODEX_HOME/<名称>.config.toml`，而非继续新增旧的 `[profiles.<名称>]` 表。配置优先级与新 profile 形式见 [OpenAI 配置基础](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence)。

应用设置页还有一句固定文案“无需后台转发服务”，应按连接模式显示：直连直接读取配置；混合连接需要模型网关；手机连接需要手机网关。关闭编辑器与停止网关是不同动作。

### 4. 增加跨字段与连接模式校验

现在 `ConfigSchema.Validate` 主要校验单项类型、枚举、长度和数值范围；`ConfigStore` 已对混合连接做部分专门保护，应保留并集中展示，而不是再增加笼统提示。

建议优先补这几组：

- `default_permissions` 与 `sandbox_mode` / `sandbox_workspace_write` 的组合；官方定义要求按不同权限模型使用，不能盲目同时写入。
- provider 的命令认证、环境变量认证、直接 bearer token 和官方认证之间的互斥关系；内置 provider ID 不作为普通可新建名称。
- MCP 的 stdio / HTTP 传输、命令或 URL、认证字段，以及超时的单位和范围；数组元素、表子项也检查，不能只证明 TOML 语法成立。
- 推理强度来自所选模型目录；Fast 开关与服务档位分别校验，并显示服务是否支持。
- 混合连接的 `file` 认证存储、原生路由和禁用请求压缩要求；这些依赖与普通直连不同。

`approval_policy` 在目录中以枚举为主，同时存在 `approval_policy.granular.*` 子项，建议提供明确的“常规 / 细分规则”表单，避免一个对象被当作普通枚举编辑。

当前 CLI 的 `features list` 连未知测试开关也可以静默接受；所以“命令退出码为 0”仍不能当成某字段被使用的证据。本次也确认 `--strict-config` 不支持 `codex features`，后续不能把这条命令包装成完整的配置验证。

### 5. 补齐远程压缩的运行诊断

这是本次最直接影响判断准确性的改进。当前 `ModelBridge` 根据 `/responses/compact` 路径把请求记为 compact；v2 在普通 `/responses` 中发送 `compaction_trigger`，因此会被记成普通 turn。

建议只统计必要元数据：压缩协议、传输方式、trigger 次数、响应 compaction item 次数、成功完成时间和错误码。HTTP/SSE 与 WebSocket 都覆盖，不能只凭 HTTP 200 判成功，也不保存聊天正文、压缩内容或凭据。

页面区分“配置允许”“客户端发出了压缩请求”“服务成功返回压缩结果”。Krill 后台没有旧端点记录，不能直接翻译成“已关闭”；供应商 ID 为 openai，也不能直接翻译成“最近成功压缩”。协议含义见 [OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

隔离结果：

| 测试 | 观察 | 能说明什么 |
| --- | --- | --- |
| `context_management=true` | 特性列表变为 true | 当前内核能识别；未证明本线路收益 |
| `token_budget.enabled=true` | 特性列表变为 true | 当前内核能识别；不能称为已失效，也不能等同远程压缩 |
| `remote_compaction_v2=true` | 仍为 removed / false | 旧开关不能用于开启或判断当前 v2 协议 |
| async_compaction 表配置 | 特性列表变为 true | 能启用开发中功能；不是稳定性或费用验证 |
| 先前本地 v2 压缩夹具 | `/responses` 中出现 trigger，并返回 compaction item | 当前协议能这样工作；不代表真实 Krill 调用成功 |

当前真实链路最近是否成功压缩仍未确认。本次没有用用户认证发起实线模型调用。

## Dock 和手机端的取舍

手机网关默认端口 13090、12 小时会话、PBKDF2 600000 次、随机管理身份和按配置目录隔离的数据，暂时没有证据需要调整。会话时长目前被 C# 与 Python 双端精确校验，不能只修改一端常量。

模型网关的 16 并发、64 MiB 上限、分阶段建连与空闲超时也先保留。后续先增加阶段耗时、等待队列、断流原因，再按数据调整；不笼统放大限制。

手机使用体验上，任务完成提醒可提供明确引导；安卓任务通知和后台通知均默认关闭，是否开启由用户按需要选择。后台常驻会影响耗电。外观、字号和思考/过程显示按阅读需求调整；图片预览或缩略图多且网络较慢时，关闭相应预览能减少加载。文件点击下载阈值目前 20 MiB，建议保留并提供常用值，避免输入极大范围导致误操作。

这些设置分别保存在浏览器、安卓、当前网关或 Codex 配置目录；不能用一个“恢复全部默认”混合覆盖。

## 建议实施顺序与验收

第一批：修正 3 处特性元数据和音频下界，记录版本来源，增加连接/权限组合校验，补 v2 压缩诊断及按连接模式显示的后台说明。验证使用隔离配置、当前二进制和本地 HTTP/SSE/WebSocket 夹具，不依赖真实用户认证。

第二批：“已配置”视图、真实动态实例、来源层、模型能力驱动的推理/档位选择，以及新 profile 文件支持。验收要覆盖带点名称、多个 MCP/provider、项目覆盖、未知字段保留、显式 false 与缺省的区别。

第三批：按需增加日常/深度配置方案、手机通知引导和连接耗时指标。方案只修改用户选择的普通设置，保留逐项预览、撤销、草稿冲突和加密备份；不附带认证、网关身份或聊天状态。

未建议重写现有保存事务、扩大权限、自动启用所有实验项、修改发布版本或重新打包。当前任务交付的是可评审的完整审查和实施方向，产品源码尚未修改。
